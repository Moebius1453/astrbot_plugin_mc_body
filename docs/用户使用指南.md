# 部署教程

适用版本：0.40.0。完成后可通过 AstrBot 控制一个独立 Minecraft 玩家，并接收游戏聊天。

请按顺序部署，每一步检查通过后再继续。功能用法见 [README](../README.md)，交给 AI 协助安装时使用 [AI 部署操作单](AI操作指南.md)。

## 1. 选择部署方式

| 方式 | 需要运行的进程 | 从哪里开始 |
|---|---|---|
| 全部放在 Windows 电脑 | AstrBot、Minecraft 独立服务端、AI 游戏客户端；亲自陪玩再开自己的客户端 | 从第2节开始 |
| 服务端放 Linux，AI 客户端放 Windows | Linux 服务端、Windows AstrBot 和 AI 客户端 | 完成第2至5节，第6节使用 SSH 隧道 |
| 已有 Minecraft 服务器 | 沿用服务端，另准备 AI 客户端和 AstrBot | 先核对第2节，再从第4节接入 |

首次部署先用有窗口的 AI 客户端，不需要 Docker、SSH 截图或无头启动器。当前不能直接连接启动器“单人游戏”打开的存档，必须使用独立服务端。

如果 AstrBot 已装在 Docker 中，先完成游戏环境；第6节不要直接照填 127.0.0.1，应使用从 AstrBot 容器实际可达的地址或容器内隧道。

## 2. 准备软件与账号

### 2.1 安装清单

| 安装位置 | 软件 |
|---|---|
| AstrBot 主机 | AstrBot 4.27及以上、低于5.0；一个支持工具调用的模型；可收发消息的平台会话 |
| Minecraft 服务端主机 | Java 21、Minecraft 1.21.1 NeoForge 独立服务端、对应 NeoForge 版本的 KubeJS 及其声明依赖 |
| AI 客户端 | Minecraft 1.21.1 NeoForge 实例、KubeJS及其声明依赖、提供 Baritone API 的 NeoForge 构建 |

通过启动器或模组发布页核对 Minecraft 版本、加载器和依赖。不要混用 Forge、Fabric 与 NeoForge 产物。KubeJS 所需依赖以所选发布文件的依赖列表为准，安装到要求的两侧。

Baritone 当前可参考的组合为 Minecraft 1.21.1 与 baritone-api-neoforge-1.11.3.jar。客户端日志必须能加载 baritone.api.BaritoneAPI；只有聊天指令可用不算通过。

若使用整合包，先使用该整合包配套的服务端包和客户端实例，再补本插件需要的模组。不要把客户端全部 mods 原样塞进服务端。

### 2.2 给 AI 准备独立账号与实例

1. 在启动器中新建或复制一个专供 AI 使用的游戏实例，启用版本隔离。
2. 为 AI 登录独立账号。开启正版验证的服务端需要有效的独立正版会话；不要让用户与 AI 用同一账号同时入服。
3. 记下 AI 的实际玩家名，例如 Alex，以及用户自己的玩家名，例如 Steve。
4. 把 KubeJS、依赖和 Baritone API 放入 AI 实例的 mods 目录。
5. 启动到游戏主菜单一次，再退出。
6. 用启动器的“打开游戏目录”找到该实例目录，确认里面有 mods、logs 和 kubejs。

不要给用户自己的客户端安装控制脚本；脚本只放到 AI 实例。

## 3. 准备独立服务端

已有可用服务端可跳过安装，直接核对模组和第4节的 RCON 设置。

### 3.1 Windows 新建服务端

1. 新建独立目录，例如 D:\Minecraft\mc-body-server，不使用启动器客户端目录。
2. 安装 Java 21，在 PowerShell 执行：

```powershell
java -version
```

通过条件：显示 Java 21。若机器有多个 Java，后续服务端启动脚本使用 Java 21 的完整路径。

3. 下载适用于 Minecraft 1.21.1 的 NeoForge 安装器。运行安装器，选择 Install server，目标目录选刚创建的服务端目录。使用整合包时优先按其服务端包说明安装，不另换加载器版本。
4. 在服务端目录运行生成的 run.bat。首次运行生成 eula.txt 后，阅读并同意 Minecraft EULA，再将其中 eula=false 改为 eula=true。
5. 先通过控制台 stop 退出服务端，再把匹配版本的 KubeJS 和依赖放入服务端 mods。
6. 重新运行 run.bat，等待控制台显示 Done。
7. 再输入 stop 正常退出，准备下一节配置。

Linux 使用配套 run.sh。已有 systemd、面板或容器服务端，按其原有方式启停，不重复创建第二个服务进程。

通过条件：未安装本插件桥脚本时，服务端已经能够正常启动，不存在模组依赖或客户端类加载导致的启动失败。

## 4. 启用并隔离 RCON

在服务端停止后，备份 server.properties，修改下面三项。密码请自行生成，不使用示例文本作为密码。

```properties
enable-rcon=true
rcon.port=25575
rcon.password=在此填写自行生成的随机长密码
```

RCON 只允许 AstrBot 通过受保护路径访问：

- 全部在本机：AstrBot 连接 127.0.0.1:25575。防火墙阻止其他主机访问25575，不在路由器做端口映射。
- 远端 Linux：在服务端宿主上使用回环地址访问 RCON，通过第6节 SSH 隧道连接。防火墙阻止外部直接访问25575。
- Docker 服务端：如需映射到宿主，只绑定 127.0.0.1:25575，不使用默认的全部网卡发布。已有容器的重建和映射变更先备份并按原部署流程处理。

rcon_host 是插件连接地址，不是服务端监听限制。server.properties 中设置密码不会自动限制监听网卡；必须检查实际监听和防火墙。不要为了 RCON 随意修改 server-ip，以免影响正常游戏连接。

Windows 可在服务端启动后查看监听：

```powershell
Get-NetTCPConnection -State Listen -LocalPort 25575
```

Linux 查看：

```bash
ss -ltn 'sport = :25575'
```

如果监听在 0.0.0.0 或 ::，继续检查并限制防火墙，不把“有密码”当作已经隔离。防火墙变更应保留原规则，远端操作不要锁断自己的 SSH。

Minecraft 游戏端口通常是25565，与 RCON 的25575不同。AI 客户端连接游戏端口，AstrBot 连接 RCON 端口。

## 5. 安装并检查两端桥

### 5.1 取得插件文件

从 [项目仓库](https://github.com/Moebius1453/astrbot_plugin_mc_body) 下载插件。后续服务端桥、客户端桥和 AstrBot 插件都使用同一份版本。

### 5.2 配置目标玩家名

打开 bridge/server/mcbridge_server.js，将开头的目标名改成第2节记录的 AI 实际玩家名。例如：

```javascript
const MCB_TARGET = 'Alex'
```

保留引号及其他代码。后续 AstrBot 的 character_name 同样填写 Alex。若实际账号就是 Nanako，可以保持默认。

### 5.3 复制脚本

| 来源 | 目标 |
|---|---|
| bridge/server/mcbridge_server.js | 服务端实例/kubejs/server_scripts/mcbridge_server.js |
| bridge/client/mcbridge.js | AI实例/kubejs/client_scripts/mcbridge.js |

已有同名文件时先备份到实例之外，不在脚本扫描目录留多个 .js 副本。KubeJS 尚未生成目录时先确认已成功加载，再创建缺少的 server_scripts 或 client_scripts 目录。

Windows 示例：将三个变量替换为自己的实际路径，再在 PowerShell 执行。执行前确认目标没有需要保留的同名文件。

```powershell
$Plugin = 'D:\Downloads\astrbot_plugin_mc_body'
$Server = 'D:\Minecraft\mc-body-server'
$Client = 'D:\Minecraft\ai-client'
New-Item -ItemType Directory -Force -Path "$Server\kubejs\server_scripts", "$Client\kubejs\client_scripts" | Out-Null
Copy-Item "$Plugin\bridge\server\mcbridge_server.js" "$Server\kubejs\server_scripts\mcbridge_server.js"
Copy-Item "$Plugin\bridge\client\mcbridge.js" "$Client\kubejs\client_scripts\mcbridge.js"
```

### 5.4 启动并检查

1. 启动或按维护安排重启服务端。已经运行且仅更新服务端脚本时，在服务端控制台输入 reload，等待加载完成。
2. 重启 AI 客户端，加入该服务端。同机填写127.0.0.1:25565；异机填写实际游戏地址和端口。
3. 服务端开启白名单时，通过其正常账号管理流程允许 AI 账号进入；不要关闭白名单来规避登录问题。
4. 在服务端控制台输入：

```text
list
mcb ping
mcb diag
mcb state
```

通过条件：

- list 能看到 AI 实际玩家名。
- mcb ping 返回以 MCB 开头的 JSON，ok 为 true，data.pong 为 true。
- mcb diag 的 targetOnline 为 true，upSeq 多次查询会增加，upAgeMs 不持续增长。
- mcb state 返回 online:true，并有可用的客户端 task 数据。

客户端 logs/latest.log 中应出现 BaritoneAPI 类可见及桥接上行相关信息。若提示 BaritoneAPI 类不可见，先换正确 API 构建，不继续接 AstrBot。

如果控制台提示没有 mcb 命令，检查服务端 kubejs/server_scripts 路径和 KubeJS 错误；角色在线但没有上报，检查 AI 客户端的 client_scripts 路径、两端 KubeJS、模组兼容性及客户端重启。

## 6. 让 AstrBot 连到 RCON

### 6.1 本机直接运行 AstrBot

后续面板填写：rcon_host=127.0.0.1，rcon_port=25575，密码使用第4节设置的密码。

### 6.2 Windows AstrBot 连接远端 Linux

先确认可以通过 SSH 登录服务端主机，再在本机 PowerShell 开一个专用终端运行：

```powershell
ssh -N -o ExitOnForwardFailure=yes -o ServerAliveInterval=30 -L 127.0.0.1:25575:127.0.0.1:25575 user@server-host
```

把 user@server-host 替换成自己的 SSH 用户与地址。首次连接核对主机指纹，按需完成身份验证。这个终端在游玩期间保持打开，Ctrl+C 关闭隧道。

后续插件依旧填写127.0.0.1:25575，不填写远端公网 IP。若本机25575已占用，将命令左侧端口改成25576，并把插件 rcon_port 改成25576；右侧25575与服务端一致。

### 6.3 AstrBot 在 Docker 中

先在部署清单记录容器网络与 RCON 所在位置：

- 两者在同一个受控 Docker 网络：使用服务名和容器内 RCON 端口，并确认该网络没有不可信容器。
- RCON 或隧道在宿主：按当前 Docker 平台设置容器到宿主的受保护访问路径，不能把宿主回环端口直接改成对外开放来解决连通问题。

先从 AstrBot 实际运行环境确认 TCP 可达，再填写面板；仅在宿主测试成功不算容器可达。网络设置不确定时，可先使用主机直接运行 AstrBot 完成接入，再单独迁移。

## 7. 安装并配置 AstrBot 插件

1. 打开 AstrBot 插件管理，使用仓库地址安装本插件：

```text
https://github.com/Moebius1453/astrbot_plugin_mc_body
```

手动安装时，把含 main.py、metadata.yaml、mcb、bridge 的完整插件目录放入 AstrBot/data/plugins/astrbot_plugin_mc_body。不要多套一层压缩包目录。

2. 在插件配置中填写：

| 配置项 | 填写内容 |
|---|---|
| rcon_host | 第6节确定的连接地址 |
| rcon_port | 第6节确定的连接端口 |
| rcon_password | 服务端 RCON 密码 |
| allowed_sender_ids | 允许控制的发送者平台 ID，例如用户的 QQ 号，按列表填写 |
| character_name | AI 实际游戏名，与 MCB_TARGET 完全相同 |
| owner_player_name | 用户自己的游戏名 |
| enable_chat_uplink | true |
| white_session | 下一步骤取得的真实会话 UMO |
| require_wake_keyword | true，先使用点名方式验收 |
| wake_keywords | 设置 AI 的称呼，例如 Alex |
| enable_sight | false，先不安装截图环境 |
| enable_self_loop | false |
| enable_event_wake | false，先不测试主动模型唤醒 |
| enable_reflex | false，先做只读连通检查 |
| enable_idle_wander | false |
| enable_hunt | false |

3. 在准备用来控制的 AstrBot 私聊或会话中正常发送一条消息；到 AstrBot 会话管理中找到它，复制其 UMO。格式为“平台实例名:消息类型:会话ID”。将实际值粘贴到 white_session，不照抄示例，也不只填写 QQ 号。
4. 确认该会话配置了工具调用模型，并选择了打算使用的人格。若人格有显式工具白名单，将 README 中的 mc_* 工具加入；原白名单中的其他工具不要删掉。
5. 保存配置并重载插件。

通过条件：日志显示插件0.40.0加载，没有未配置 RCON 密码、无允许调用者或 white_session 缺失的告警。allowed_sender_ids 为空时全部拒绝，不能先留空再测试控制。

## 8. 验收接入

### 8.1 不经过模型的连接检查

从授权的 AstrBot 会话发送：

```text
/mcbody
```

应返回桥连通及诊断数据。若拒绝权限，修正 allowed_sender_ids；若连接失败，回第4和第6节检查。

### 8.2 模型工具检查

从同一会话要求模型读取状态和背包，不执行动作：

```text
请调用 mc_state 和 mc_inventory，只告诉我结果，不移动、不使用物品。
```

通过条件：AstrBot 日志中存在真实工具调用，返回角色在线、位置和库存；只有文字答复不算通过。

### 8.3 游戏聊天检查

由另一位玩家进入服务端，在游戏聊天里发送包含唤醒词的普通消息，例如“Alex，能听见吗”。

通过条件：AstrBot 产生一轮上行处理，AI 回复出现在游戏公屏。该步骤会调用模型并写入所选会话；使用新测试会话可避免混入个人常用历史。

聊天接通后，require_wake_keyword=false 可免点名，但所有其他玩家聊天均可能触发，不限身份和距离。不要在公共服务器未经评估就关闭点名要求。

### 8.4 动作检查

在测试存档或已备份的安全区域，选择地面上可步行到达的近点，要求移动几格，再用 mc_state 核对坐标，最后要求调用 mc_stop。

通过后，再按需要开启 enable_reflex、enable_idle_wander、enable_hunt 和 enable_event_wake，保存并重载。测试期间关闭保命反射时不要把角色留在危险环境。普通移动可能破坏挡路方块，正式存档使用前先核对 Baritone 设置和保护效果。

## 9. 可选：远端无头客户端和截图

仅需要移动、聊天和物品交互时，部署到第8节即可。本节只适用于已有 Linux Docker 客户端环境的用户，不是从零自动安装无头游戏的流程。

### 9.1 核对现有容器

按实际容器名检查以下条件：

- 游戏进程运行在 DISPLAY=:99 的 Xvfb 上。
- 容器安装 ImageMagick，能够执行 import。
- 容器内游戏目录可写，存在 /data/client/shots/。
- 容器 /data/client 绑定挂载到宿主 /data/mc-brain/client。
- AstrBot 主机能通过免密 SSH 登录客户端宿主，能用 scp 读取宿主截图文件。
- Docker 权限已配置；需要 sudo 时，插件通过 client_sudo_password 提供凭证。

当前截图代码使用固定路径：容器 /data/client/shots/mcb_look.png，宿主 /data/mc-brain/client/shots/mcb_look.png。仅修改 client_container 不会改变这些路径。不采用上述挂载结构时，需先调整截图实现，不能仅靠面板设置完成。

在客户端宿主检查截图，下面的 mc-brain 换成实际容器名；权限不足时按本机现有方式使用 sudo：

```bash
docker exec mc-brain bash -c 'DISPLAY=:99 import -window root /data/client/shots/mcb_look.png'
```

打开生成的图片，确认不是黑屏且有游戏画面，再接视觉模型。

### 9.2 填写截图配置

| 配置项 | 内容 |
|---|---|
| enable_sight | true |
| client_ssh_host | 客户端宿主 SSH 目标，格式 user@host |
| client_container | 游戏容器名 |
| client_sudo_password | 需要 sudo 时填写，否则留空 |
| vision_provider_id | AstrBot 中已配置的视觉提供商 ID |

重载插件，调用一次 mc_screenshot。通过条件：产生真实截图并返回画面描述。该操作会将图片发送给视觉提供商并产生费用。

bridge/launcher/Dockerfile 只提供运行依赖，不会自动准备游戏文件或启动 Xvfb；client.py 使用固定实例名、离线身份和 Linux 文件锁。不要直接拿来登录正版验证服务器，或当作 Windows 通用启动器。需要无头化时，先单独完成游戏实例、认证、虚拟显示及自动启动，再回本节验收。

## 10. 更新与故障定位

更新前备份服务端脚本、AI 客户端脚本、AstrBot 插件目录和配置。保留世界、data/uplink_state.json、data/places.json及自定义 places_file。不要用旧部署目录整体覆盖运行数据。

| 更新内容 | 生效方式 |
|---|---|
| AstrBot 插件 | 复制到实际插件目录后重载 |
| 服务端桥 | 复制到 server_scripts 后执行 reload |
| 客户端桥 | 复制到 AI 实例 client_scripts 后重启 AI 客户端 |
| mods、server.properties | 按维护安排重启对应游戏进程 |

| 卡在哪一步 | 查哪里 |
|---|---|
| AI 进不了服务器 | 客户端 logs/latest.log、服务端 logs/latest.log、账号认证、白名单、两侧模组 |
| 没有 mcb 命令 | 服务端 kubejs/server_scripts、logs/kubejs/server.log |
| targetOnline=false | list 中的实际名字是否等于 MCB_TARGET |
| upSeq 不增加 | AI 客户端 logs/latest.log、logs/kubejs/client.log（若该版本生成）、BaritoneAPI 加载及两端 KubeJS |
| 宿主通，AstrBot 不通 | AstrBot 是否在容器中，连接地址是否从实际运行环境可达 |
| /mcbody 无权限 | 发送者实际平台 ID、allowed_sender_ids |
| 模型没有工具 | 人格工具白名单、插件加载日志、模型工具调用支持 |
| 游戏不回复 | white_session、唤醒词、上行开关、会话模型和身份权限 |
| 新文件没生效 | 实际加载目录、重复同名插件、是否完成对应重载或重启 |

提交故障信息时提供操作系统、组件版本、卡住的步骤及同一时间的脱敏日志，不提交账号令牌、RCON 密码或完整私人聊天记录。
